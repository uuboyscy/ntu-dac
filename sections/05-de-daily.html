05 / DE DAILY

資料工程師的日常，
大部分不在 demo 裡

寫 Pipeline 只是其中一段。更長的時間，花在問清楚、處理例外、讓流程能重跑、讓告警有人看，以及把系統交給下一個人。

這一段讓學生建立實際期待。別把 DE 簡化成 ETL，也別把維運講成無聊雜事；可靠性就是從這些工作累積出來的。

05 DE 的工作迴圈

一個需求進來，
工程師先處理這些問題

1. 問清楚來源與用途

誰產生？誰使用？更新多久？成功的定義是什麼？

2. 選擇處理方式

批次、微批次或即時；重點是匹配決策時點與失敗成本。

3. 建立可重跑的流程

轉換邏輯、資料模型、重試、回補與版本控制都要想。

4. 讓錯誤先被看見

品質、freshness、schema 變更、告警與責任人。

5. 交付給下游，遇到新問題再修

和 DA、DS、產品、資安與營運一起處理新需求。

INPUT

資料契約

欄位、型別、更新頻率、擁有者與變更規則。

PROCESS

Pipeline

能觀測、能重跑、能處理延遲與部分失敗。

CONTROL

品質與血緣

知道哪個檢查失敗，也知道影響哪些下游。

HANDOFF

文件與告警

讓另一個人接手時，不必只靠口頭記憶。

工程最後要交付的是一條能重跑的 Pipeline，讓下游在關鍵時刻敢用這份資料。

這張約 6 分鐘。可以挑一個工作日常說明：很多時間花在上游欄位變更、資料延遲、回補、告警與下游定義不一致。

提醒學生：這些事情聽起來不炫技，卻決定資料平台是否能被信任，也決定你是否能從「會寫」成長為「能負責」。

05 DE 的判斷力

需求說要即時，
架構也要先算過

資料工程師會一起看更新頻率、可靠度、團隊能不能維護，以及成本，再決定要不要把架構做複雜。

先問四件事

  • 決策什麼時候發生？
  • 延遲多久會造成實際損失？
  • 尖峰流量與重放需求如何？
  • 團隊是否有能力長期維運？

再比較三種方案

  • Batch：簡單、便宜、適合固定週期。
  • Micro-batch：縮短等待，但仍保留部分可控性。
  • Streaming：反應快，但狀態、重放、順序、監控與成本都更複雜。

最後選的方案，要對應需求，也要說清楚風險和代價。

這張約 5 分鐘。streaming 在該用的地方很重要。重點放在「即時」要由業務決策時點與風險推導，不能只看工具熱度。

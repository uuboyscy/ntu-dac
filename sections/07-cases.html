06 案例一 · DATA PLATFORM

把分散的電商資料，
整成共用資料平台

電商數據中台專案

THE PROBLEM

資料量不大，
但來源與邏輯很分散

各部門的報表邏輯與排程散在不同地方，出錯後不易追查或補資料。

整理後 報表邏輯與排程集中管理；有問題時，能追來源、重跑或補資料。

32:00–36:00｜4 分鐘

先說問題：電商資料量不一定大，難處在會員、商品與報表邏輯散在各處，排程和補資料不易一起管理。

沿圖走一次：來源載入 BigQuery，由 dbt 分層整理，提供報表與其他下游使用；Prefect 集中安排與觀察流程。Data Fusion、Python、Cloud Storage 是不同來源的載入方式，不必逐一解釋每種工具。

說明取捨：把報表加工邏輯與排程集中，方便同一個團隊維護，也要求共用的指標口徑、品質檢查和來源追溯。這頁沒有量化成效，口頭不要補未確認的節省時間或錯誤率。

收在個人觀察：資料工程的工作不只把資料放進平台，還要讓下一個使用者知道數字從哪裡來、出錯時怎麼查。

36:00–41:00｜5 分鐘

先講舊流程的兩個痛點：程式得上傳伺服器才執行，提交後難查任務狀態與錯誤紀錄。不要逐條朗讀左欄。

沿主圖走一次：Client 向 API 提交任務取得 Job ID，Queue 讓任務排隊等待處理，Consumer 背景啟動 Spark，結果存入 HDFS；MySQL 留下可查詢的任務狀態與輸出路徑，Log System 集中看執行紀錄。備查：此案例的 Queue 使用 RabbitMQ；訊息持久化、確認與移除的時機取決於實際設定，不延伸未核對的重試機制。

問聽眾一個問題：任務失敗時，提交者怎麼知道停在哪裡？用 ready、running、done／error 和 Log 說明「可追蹤」的價值。

底部時間圖只作流程演進的概略說明：原先 MapReduce 約 7–8 小時，改用 Spark 並整合後續系統後約 1–2 小時；不要把這說成 Queue 單獨帶來的效果，也不當成兩個引擎的嚴格效能比較。

收在取捨：提交與執行分開後，狀態能查，但系統也多了狀態同步與監控工作。下一段談 AI 時代，仍要有人理解這些系統責任。

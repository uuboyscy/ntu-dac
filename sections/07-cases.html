06 案例一 · DATA PLATFORM

把分散的電商資料，
整成公司共用的數據底座

電商數據中台專案

但來源與邏輯很分散

DATA TEAM 集中控管資料邏輯與排程
SHARED DATA PLATFORM 來源載入、分層轉換，再提供各團隊使用

約 4–5 分鐘。分享節奏：0:00–1:00 說明資料量不大、難處在資料和處理邏輯分散；1:00–2:30 走一次來源、載入、BigQuery/dbt 分層與下游的資料路徑；2:30–3:30 說明 Prefect 如何統一排程，讓 Data team 管理執行與重跑／補資料；3:30–4:30 收束到數據治理：報表口徑、品質檢核與來源追溯。

背景與問題：這是電商平台相關專案。原本資料量不算大，但線上會員、線下會員、商品與會員標籤等資料分散；公司層級報表所需的加工邏輯與排程也分布在不同地方。維護時要找出資料在哪裡處理、由哪個排程產生；出錯後要重跑或補資料，也不容易由同一團隊統一管理。

架構圖說明：圖中資料來源包含資料庫／會員資料、檔案、API 與使用者行為；依來源透過 Data Fusion、Python 或 Cloud Storage 載入 BigQuery。進入 BigQuery 後由 dbt 按 Source、ODS、STG、Dimensions & Details、Mart 分層整理，再供 Power BI、Data Science 工作流程、CDP／MA 與 Reverse ETL 使用。這些載入工具是來源路徑的組合，不代表每種資料都依序通過每個工具。

排程與治理：Prefect 用來集中編排與監控資料流程，讓 Data team 統一管理排程、執行狀態，以及失敗後的重跑與補資料。重點不只是把資料放進 BigQuery，而是把原本散落各處的報表加工邏輯收斂到 Data team，使共用資料模型有一致的責任窗口。

保留的工程核心：資料平台集中後，仍需定義各層資料的口徑與粒度，對轉換結果做品質檢核，並保留來源追溯。這延續原案例「資料可信、出了問題能定位」的目標，但不再把故事聚焦在金融業身份橋接或模型特徵工程。

資訊邊界：架構名稱與來源／工具／分層／下游依 Allen 提供的圖與描述整理。沒有提供精確資料量、表數、排程頻率、節省時間或錯誤率，因此本頁不宣稱量化效能提升、特定 SLA 或正式治理指標；口頭補充前請先確認可公開的專案範圍與工具實際使用方式。

這張約 4–6 分鐘。分享節奏規劃：0:00–1:00 講原本痛點與人工流程限制；1:00–2:30 拆解 Job Queue API 架構與 RabbitMQ／MySQL 的責任分工；2:30–3:30 用一個任務失敗的情境說明狀態追蹤與排錯；3:30–4:30 說明每日流程時間是概估，以及為什麼不能把改善歸因於 Queue；4:30–5:30 收束到工程取捨與資料工程職涯啟示。

原本的工作方式與痛點：原始投影片整理出舊有流程：編輯程式 → 上傳到伺服器 → Crontab 或人工執行。當時面臨的痛點不只是執行速度慢，而是責任混在一起：Spark 程式不易呼叫、大量 Log 集中難以排查、ETL 邏輯全部綁在單一腳本不易維護，且執行進度與狀態完全不可追蹤。

架構流程與非同步邊界：重構後分為清楚的水平鏈路：Client 透過 REST API 提交任務，API 建立 Job ID 並立即回傳，同時將工作推送到 RabbitMQ ready queue；Consumer 訂閱 queue，取出任務後啟動 Spark 分散式運算；處理後的資料寫入 HDFS。這當中的「非同步邊界」在於：Client 與 API 完成提交後就結束同步等待，後續排隊與 Spark 執行完全在背景進行，避免長時間佔用連線。

為什麼 RabbitMQ 負責任務傳遞／排隊，而 MySQL 負責持久化狀態／metadata：這代表兩種完全不同的系統責任。RabbitMQ 是傳遞性、暫態的訊息佇列，專長是緩衝削峰、任務解耦與分派（Consumer 處理完即消費刪除），但不適合用來做狀態查詢、複雜關聯或長期追蹤；MySQL 則是持久化儲存，負責保存 Job ID、請求參數、SQL 內容、目前狀態與產出路徑。兩者搭配是為了讓「任務分派」與「狀態查詢」各自獨立演進。另外 Log System 則專門收集 Spark 執行日誌，讓排查錯誤不必回到各節點翻查檔案。

Job lifecycle：以 ready → running → done／error 追蹤。API 建立任務時寫入 ready，Consumer 取出任務並啟動 Spark 時更新為 running，Spark 成功結束寫入 HDFS 則更新為 done，若執行失敗則記錄為 error。提交者可憑 Job ID 隨時回到 API／MySQL 查詢目前狀態與輸出路徑。

用一個問題帶出狀態追蹤：任務排隊後如果執行失敗，提交者怎麼透過 Job ID 知道它停在哪個狀態、去哪裡看 Log？這說明了為什麼任務狀態要能查、執行紀錄要能集中查看。把它當成架構判斷的提問，不延伸宣稱自動重試或補救機制已經實作。

每日資料管線時間的解讀：依 Allen 這次提供的概略回憶，原本使用 MapReduce 時，每日流程可能需要約 7–8 小時；後來改用 Spark，並整合 Job Queue 系統後，整體約 1–2 小時可完成。這是整體流程的概估，不是各處理引擎的獨立 benchmark；不能把全部改善歸因於 Queue。個別作業、資料範圍、硬體、是否計入排隊時間與計時口徑可能不同，精確數據仍待確認。

工程 Trade-off：做系統不是盲目加技術。換回的是：提交與執行解耦、任務狀態可查、運算引擎可獨立擴展；付出的代價則是：狀態機一致性、訊息重複消費防範與監控維運成本。

資訊邊界與待 Allen 確認事項： 1. 原始投影片支持的事實：Client／REST API／RabbitMQ／MySQL／Consumer／Spark／HDFS 元件架構；ready／running／done／error 狀態劃分；從 MapReduce 改用 Spark、後續整合 Job Queue 系統的演進；原本人工執行與 Log 難查之痛點；Git Flow 多 feature 分支規劃。個別產品耗時不在本頁呈現。 2. 整理出的教學推導：4–6 分鐘節奏配置；提交／佇列／執行／觀測之責任解耦視角；RabbitMQ 與 MySQL 各司其職之設計理由；用任務失敗的提問說明狀態追蹤與排錯；工程取捨的整理方式。 3. 待 Allen 確認事項：Gamania 公司名稱是否可公開具名；專案發生年份、團隊規模與個人實際負責項目；概估時間的資料範圍、硬體、是否包含排隊時間與測量口徑；RabbitMQ 的 ack／retry／DLQ／重複消費防範機制；MySQL 與 Queue 一致性設計；系統是否正式 production 上線及維運規模。 4. 本頁不宣稱的事項：不宣稱正式 SLA、生產環境零故障、完整自動重試機制，不加入來源沒有證據的 scp、跳板機、ps aux、HTTP 202/200、Spark Driver、幾百 MB Log 等未證實細節。

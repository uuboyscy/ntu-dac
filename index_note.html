這一段先建立共同底圖。資料職位變重要，是因為企業開始把資料當成持續運作的基礎設施，也需要有人把一次性的整理工作變成穩定流程。

再補充各段工作的差異：資料工程在中間承擔的是把來源的混亂整理成下游可依賴的介面；分析與模型則把資料整理成能回答問題的指標、比較和證據。這兩種工作不是分開的兩條路，而是在同一條路徑上接力。

最後收在下方三個價值：公司真正需要的不是某一個特定平台，而是把資料做得更快、更穩，讓人敢拿來做決策。可以問大家：如果你看見一個 dashboard，會想往左追問哪一段？

02 為什麼是現在？

資料職位為什麼在這幾年變多？

資料一旦進入營運，錯一次就不只是報表錯；庫存、行銷、風控與客戶服務都可能跟著錯。

01 / DAILY

資料變成每天都要跑的系統

流程不是跑完一次就結束。半夜斷掉、隔天才發現，報表、推薦或營運數字就會一起延遲。

02 / DEFINITION

同一個數字，常常有不同答案

不同團隊各自計算營收或活躍用戶，大家都能交報表，卻沒有人能說明哪個才是基準。

03 / SCALE

資料量變大，錯誤也變得更貴

查詢變慢、回補變久、雲端費用上升。問題不再只是能不能算，而是能不能穩定地算下去。

04 / AI

AI 越快，越快暴露資料問題

模型可以很快給答案，但來源過期、欄位定義不一致，回答再順也可能是錯的。

資料職位變多，是因為資料已經從分析素材，變成會影響營運的系統。

這張約 5 分鐘。這頁不是要說「資料變多，所以需要資料工程師」這麼簡單。真正的變化是：資料開始進入每天的營運流程，一次錯誤會沿著下游傳出去。

可以依序講四個痛點：流程需要每天穩定跑；不同部門對同一個指標有不同定義；資料量放大後，速度、回補與成本都變成工程問題；AI 讓答案產生得更快，也讓錯誤定義與過期資料更快被放大。

收尾時強調：資料職位增加，不是因為工具名稱變多，而是資料已經會影響庫存、行銷、風控與客戶服務。

03 / ROLE MAP

DA、DS、DE，處理不同的資料問題

DA 把資料轉成洞察，DS 建立預測與模型，DE 確保資料穩定流動。

這一段用問題與產出去講三個角色。不同公司會重疊，尤其小團隊一個人可能同時做兩三種事。

這張約 6 分鐘。DA 會問期間、回補與去重規則；DS 會問特徵是否可用、歷史資料與品質是否足夠；DE 則看影響範圍、監控與如何恢復。

三個角色名稱中英對照：DA（Data Analyst 資料分析師）、DS（Data Scientist 資料科學家）、DE（Data Engineer 資料工程師）。DA 側重定義與洞察，DS 側重假設與預測證據，DE 側重管線穩定、資料契約與可追溯重跑。不同公司會有不同邊界與重疊；特別在小團隊，一人可能包辦從資料管線到報表分析。

引導學生思考：不需要急著幫自己貼標籤，而是看自己願意長期面對哪類挫折與挑戰——是面對模糊需求並勇敢下定義（DA）、是在不確定中接受假設可能被推翻（DS），還是反覆處理管線失效、重跑回補與底層維運（DE）。接下來用會員流失情境，看這些問題如何在同一個團隊裡接起來。

這張約 6 分鐘。用會員流失案例把三種工作接起來。DA 的定義會影響 DS 的標籤，DS 的需求會影響 DE 的資料契約；業務的決策成本則會反過來決定要不要做模型。

三個底部詞是交付前的最低共識：先把問題定義清楚，再確認資料與結果的限制，最後留下更新頻率、owner、失效訊號與回補方式。合作不是把工作切開，而是讓下一個人不用重新猜前面發生了什麼。

04 DE DAILY

DE 的日常，
不是把 Pipeline 寫完就結束

每個需求都要在即時性、可靠度、維運能力與成本之間做選擇。

1. 問清楚來源與用途

誰產生、誰使用、多久更新，成功的定義是什麼？

2. 選批次、微批次或即時

由決策時點與失敗成本推導，不先追工具熱度。

3. 建立可重跑的流程

轉換、重試、回補與版本控制都要能走得通。

4. 讓錯誤先被看見

品質、freshness、schema、告警與 owner 要連起來。

5. 交付給下游，持續修

文件、血緣與新需求都會回到這條工作迴圈。

INPUT

資料契約

欄位、型別、更新頻率、擁有者與變更規則。

PROCESS

Pipeline

能觀測、能重跑，也能處理延遲與部分失敗。

CONTROL

品質與血緣

知道哪個檢查失敗，也知道影響哪些下游。

HANDOFF

文件與告警

讓下一個人接手時，不必只靠口頭記憶。

即時不是預設答案；選的方案要對應需求，也要能長期維護。

這張約 6 分鐘。這頁把 DE 的日常和架構判斷放在一起。很多時間花在上游欄位變更、資料延遲、回補、告警與下游定義不一致，不只是寫 Pipeline。

Batch、Micro-batch、Streaming 都是選項，不是職稱或能力高低。即時需求要由業務決策時點、延遲損失、重放需求、團隊維運能力與成本推導。最後收在四個交付物：資料契約、能重跑的 Pipeline、品質與血緣、文件與告警。

第一個轉折，金融業數據團隊：剛進去時，團隊沒有明確定義「資料工程師」這個角色。我做資料處理、分析、資料庫，也接觸大數據系統管理。當時還沒有很強烈地認定這就是我的興趣，只是開始注意到自己對資料如何流動有點好奇。

第二個轉折，新創資料產品：我的職稱是後端工程師，工作有維護 API，也有一大部分要在 Hadoop 相關系統處理資料。這時我比較確定，自己喜歡大數據處理、讓資料跑得更快，也喜歡管理 infra。後來進入遊戲公司，面對更大的資料規模，學到更多 Hadoop 與大數據框架；這段工作把技術底子做深了。

第三個轉折，從遊戲公司轉向數據治理：大規模系統很有挑戰，但也很累。有時錯誤訊息和真正的 root cause 對不上，除錯會花很多力氣。我也發現自己在專案控管、理解業務端在意什麼方面還有不足。剛好獵頭介紹一個數據治理相關職位，我可以把業務需求轉成技術方案，也要控專案進度。做了一段時間後，我發現自己更喜歡數據治理、規劃架構和雲端架構，於是繼續往資料與雲端架構深耕，現在的正式職稱為 Engineering Lead（Cloud & Data），主要負責雲端架構與資料架構的技術決策，並持續進行跨團隊協作。

講述時的重點：不要把這條路說成事先規劃好的升遷階梯。金融業是接觸資料工作的起點；新創讓興趣變得具體；遊戲公司讓我累積大規模系統經驗，也讓我看見只會處理系統問題不夠；數據治理工作則讓我確認自己喜歡把業務需求、專案與架構接起來。

保留的工程核心：資料平台集中後，仍需定義各層資料的口徑與粒度，對轉換結果做品質檢核，並保留來源追溯。這延續原案例「資料可信、出了問題能定位」的目標，但不再把故事聚焦在金融業身份橋接或模型特徵工程。

資訊邊界：架構名稱與來源／工具／分層／下游依 Allen 提供的圖與描述整理。沒有提供精確資料量、表數、排程頻率、節省時間或錯誤率，因此本頁不宣稱量化效能提升、特定 SLA 或正式治理指標；口頭補充前請先確認可公開的專案範圍與工具實際使用方式。

  • 每個任務都有 Job ID，可追蹤 ready／running／done／error 狀態

這張約 4–6 分鐘。分享節奏規劃：0:00–1:00 講原本痛點與人工流程限制；1:00–2:30 拆解 Job Queue API 架構與 RabbitMQ／MySQL 的責任分工；2:30–3:30 用一個任務失敗的情境說明狀態追蹤與排錯；3:30–4:30 說明每日流程時間是概估，以及為什麼不能把改善歸因於 Queue；4:30–5:30 收束到工程取捨與資料工程職涯啟示。

原本的工作方式與痛點：原始投影片整理出舊有流程：編輯程式 → 上傳到伺服器 → Crontab 或人工執行。當時面臨的痛點不只是執行速度慢，而是責任混在一起：Spark 程式不易呼叫、大量 Log 集中難以排查、ETL 邏輯全部綁在單一腳本不易維護，且執行進度與狀態完全不可追蹤。

架構流程與非同步邊界：重構後分為清楚的水平鏈路：Client 透過 REST API 提交任務，API 建立 Job ID 並立即回傳，同時將工作推送到 RabbitMQ ready queue；Consumer 訂閱 queue，取出任務後啟動 Spark 分散式運算；處理後的資料寫入 HDFS。這當中的「非同步邊界」在於：Client 與 API 完成提交後就結束同步等待，後續排隊與 Spark 執行完全在背景進行，避免長時間佔用連線。

為什麼 RabbitMQ 負責任務傳遞／排隊，而 MySQL 負責持久化狀態／metadata：這代表兩種完全不同的系統責任。RabbitMQ 是傳遞性、暫態的訊息佇列，專長是緩衝削峰、任務解耦與分派（Consumer 處理完即消費刪除），但不適合用來做狀態查詢、複雜關聯或長期追蹤；MySQL 則是持久化儲存，負責保存 Job ID、請求參數、SQL 內容、目前狀態與產出路徑。兩者搭配是為了讓「任務分派」與「狀態查詢」各自獨立演進。另外 Log System 則專門收集 Spark 執行日誌，讓排查錯誤不必回到各節點翻查檔案。

Job lifecycle：以 ready → running → done／error 追蹤。API 建立任務時寫入 ready，Consumer 取出任務並啟動 Spark 時更新為 running，Spark 成功結束寫入 HDFS 則更新為 done，若執行失敗則記錄為 error。提交者可憑 Job ID 隨時回到 API／MySQL 查詢目前狀態與輸出路徑。

用一個問題帶出狀態追蹤：任務排隊後如果執行失敗，提交者怎麼透過 Job ID 知道它停在哪個狀態、去哪裡看 Log？這說明了為什麼任務狀態要能查、執行紀錄要能集中查看。把它當成架構判斷的提問，不延伸宣稱自動重試或補救機制已經實作。

每日資料管線時間的解讀：依 Allen 這次提供的概略回憶，原本使用 MapReduce 時，每日流程可能需要約 7–8 小時；後來改用 Spark，並整合 Job Queue 系統後，整體約 1–2 小時可完成。這是整體流程的概估，不是各處理引擎的獨立 benchmark；不能把全部改善歸因於 Queue。個別作業、資料範圍、硬體、是否計入排隊時間與計時口徑可能不同，精確數據仍待確認。

工程 Trade-off：做系統不是盲目加技術。換回的是：提交與執行解耦、任務狀態可查、運算引擎可獨立擴展；付出的代價則是：狀態機一致性、訊息重複消費防範與監控維運成本。

資訊邊界與待 Allen 確認事項： 1. 原始投影片支持的事實：Client／REST API／RabbitMQ／MySQL／Consumer／Spark／HDFS 元件架構；ready／running／done／error 狀態劃分；從 MapReduce 改用 Spark、後續整合 Job Queue 系統的演進；原本人工執行與 Log 難查之痛點；Git Flow 多 feature 分支規劃。個別產品耗時不在本頁呈現。 2. 整理出的教學推導：4–6 分鐘節奏配置；提交／佇列／執行／觀測之責任解耦視角；RabbitMQ 與 MySQL 各司其職之設計理由；用任務失敗的提問說明狀態追蹤與排錯；工程取捨的整理方式。 3. 待 Allen 確認事項：Gamania 公司名稱是否可公開具名；專案發生年份、團隊規模與個人實際負責項目；概估時間的資料範圍、硬體、是否包含排隊時間與測量口徑；RabbitMQ 的 ack／retry／DLQ／重複消費防範機制；MySQL 與 Queue 一致性設計；系統是否正式 production 上線及維運規模。 4. 本頁不宣稱的事項：不宣稱正式 SLA、生產環境零故障、完整自動重試機制，不加入來源沒有證據的 scp、跳板機、ps aux、HTTP 202/200、Spark Driver、幾百 MB Log 等未證實細節。

07 / AI ERA

AI 會改變工作內容，
結果仍要有人負責

程式與答案產生得更快之後，問題定義、驗證、系統脈絡與責任判斷會更常出現在日常工作裡。

這一段別做成 AI 工具清單。重點是哪些能力會被放大、哪些責任不能外包給模型。

07 AI 會改變什麼？

AI 讓產出變快，
錯誤也可能走得更遠

被加速的部分

  • 把自然語言轉成 SQL、程式或文件初稿
  • 探索資料、解釋錯誤、產生測試案例
  • 比較常見架構與實作方式
  • 讓一個人先做出原本要多人一起起手的初版

因此更重要的部分

  • 判斷需求與資料是否真的對得上
  • 驗證答案、理解邊界、找出模型沒看見的例外
  • 知道權限、資安、成本與穩定性不能靠猜
  • 為上線後的結果、失效與影響範圍負責

AI 可以很快寫出答案；能不能上線，還是要由工程和業務一起判斷。

這張約 5 分鐘。承認 AI 會提高個人產出，避免用「AI 不會取代人」這種空泛句子帶過。產出速度提高後，驗證、脈絡與責任會更重要。

07 怎麼準備？

寫程式之外，
也要學會審查 AI 寫的系統

01 / FOUNDATION

把底層補起來

SQL、Python、資料結構、網路、Linux、版本控制與基礎統計。基礎不夠，很難知道答案哪裡不對。

02 / CONTEXT

學會看完整流程

不能只看一段 query；還要追來源、轉換、儲存、權限、部署、監控與下游使用。

03 / EVIDENCE

用測試與觀測驗證

用資料測試、效能測試、錯誤情境與真實案例去驗證它。「看起來合理」還不夠。

04 / JUDGEMENT

練習說清楚取捨

為什麼這樣做？成本是什麼？什麼情況會失效？誰需要知道？這些問題比 prompt 技巧更耐用。

AI 讓初版更快；真正拉開差距的是，你能不能把結果驗清楚，並對它負責。

這張約 5 分鐘。給學生具體路徑：底層、脈絡、證據、判斷。可以示範讓 AI 產生一段 SQL，但接著問資料定義、NULL、重複、時區與效能，讓大家看到審查比生成更關鍵。

BEFORE CALLING IT DONE

能測試，也能處理失敗

  • 測試資料品質、轉換結果與邊界情況
  • 失敗處理告警、重試、避免重複寫入、補資料
  • 擴展資料量增加後的延遲、成本與瓶頸
  • 交付架構圖、可驗證結果與已知限制
資料流不只要跑通，還要能說明、能驗證、出錯能處理。 把假設、測試與取捨一起放進作品。

這張約 4–5 分鐘。重點不是規定幾天做完，而是讓作品呈現一條完整、能被追問的資料流。

先定義問題：先說清楚誰需要這份資料、要做什麼決策，或原本哪個工作很難完成。問題定不清楚，後面即使把資料搬進倉庫，也可能沒人會用。

確認資料與處理：列出資料來源、來源負責人、權限、更新頻率與資料限制，再說明清理、關聯、轉換和結果粒度。用一張架構圖交代資料如何流動，以及為什麼選批次或即時處理、如何選儲存和排程方式。

驗證可靠性：準備幾種測試：輸入資料品質、轉換結果、空值／重複等邊界情況，以及流程失敗時是否能發現。再說明重試、避免重複寫入和補資料如何設計；如果資料量增加，估計哪裡會先成為瓶頸，成本和延遲如何變化。

交付作品：讓別人能看懂問題、資料來源、處理步驟、架構取捨、測試結果和已知限制。作品不必包成產品，也不必一開始就做很大，但要能說明它解決什麼問題，以及資料流在正常和失敗時各怎麼運作。
